=====================================================================
UNIVERSAL RISK CHECKLIST (verify each that applies; skip those that do not)
=====================================================================
Look for these classic failure patterns, adapted to the detected stack:
- Entry points (routes, resolvers, RPC methods, sockets, webhooks, queue consumers,
  cron jobs) missing authentication, authorization, input validation, rate limiting
  or tenant scoping that sibling entry points have.
- Inconsistent guard coverage: the same kind of resource protected in one module
  and unprotected in another.
- Tenant or ownership identity taken from client-supplied input instead of verified
  identity; queries missing the tenant/owner predicate; updates or deletes keyed by
  ID alone; nullable or optional tenant columns; cache keys, file paths, job
  payloads, events or logs lacking tenant scope; list or aggregate endpoints that
  count or return data outside the caller's permitted scope.
- Realtime channels (WebSocket, SSE, pub/sub) without authentication or tenant
  checks; permissive CORS; credentials or tokens in URLs.
- Code that is defined but never wired: handlers with no subscriber, workers with
  no registration or schedule, routes not mounted, feature flags never read,
  dispatchers with no caller, migrations never applied.
- Asynchronous work: non-durable or process-local idempotency, missing retry or
  dead-letter handling, jobs enqueued outside the transaction that justifies them,
  dual writes without an outbox or equivalent, unbounded retries, no per-tenant
  concurrency control, missing correlation IDs.
- Client/server contract drift: field names, types, enums or filters that differ
  between caller and receiver; silently ignored unknown fields; defaults that hide
  mismatches.
- Partially implemented options: enum values or presets that fall through to a
  default; settings stored but never honored (timezone, locale, currency); hard-
  coded constants that were meant to be configuration.
- Missing audit trail on sensitive actions (exports, downloads, permission changes,
  financial or destructive operations).
- Data handling: money as floating point, mixed currencies summed, unbounded queries
  or missing pagination, O(n) cache invalidation commands, N+1 queries, missing
  indexes on filter/sort columns, large payloads without limits.
- Secrets and config: secrets committed, unvalidated environment variables,
  differing behavior by environment that is not documented.
- Dependency and supply-chain basics: unpinned or abandoned critical dependencies,
  no lockfile, known-vulnerable versions if checkable offline.
- Operational gaps: no graceful shutdown, no health/readiness checks, no timeouts,
  no backups or migration strategy visible, no CI.
- Documentation drift: stack, versions, features or status claimed in docs that the
  code contradicts.
Also verify each item in KNOWN_CONCERNS independently and report it as CONFIRMED,
REFUTED or PARTIAL. Do not assume it is true because it was written down.

A. entry-point-inventory.md
   Table of EVERY entry point of every kind found in discovery: HTTP routes,

B. Diagrams (one file each; every node links to its source file where the tool
   allows; choose only the types that apply from this catalog and say which you
   skipped):
   1. Architecture: runtime topology of all deployable units and external systems.
   2. Sequence: the standard guarded request, from entry to response, including
      auth, scope resolution, authorization, business logic, data access,
      transaction, and side effects (events, audit, jobs).
   3. Sequence: any entry point whose guard chain differs from the standard one
      (reports, bulk/export, admin, portfolio-wide, public, webhook).
   4. Sequence: each long-running or asynchronous flow (export, import, email,
      payment, AI task, file processing), including threshold or fallback paths,
      artifacts, retention and cleanup.
   5. Data flow: identity and tenant/ownership scope propagation through token,
      middleware, queries, cache keys, jobs, events, storage paths, audit, telemetry;
      mark every place the scope is dropped or optional. (Skip tenant parts if the
      system is single-tenant; instead show user/ownership scope.)
   6. Data flow: event, messaging and notification pipeline end to end, marking
      unwired stages.
   7. Sequence: authentication and account flows that exist (signup, login, token
      refresh/revocation, verification, reset, SSO/OAuth, invitations, MFA).
   8. Architecture: module/package dependency map including shared packages; show
      cycles or boundary violations.
   9. Lifecycle: state machines for jobs, domain records with status fields, and
      notifications.
   10. Workflow: the main business processes as the code implements them.
   After each diagram, list edges you could not verify. If a diagram would be mostly
   UNVERIFIED, say so instead of filling gaps.

C. findings.md
   Every confirmed issue, from the universal checklist, KNOWN_CONCERNS and anything
   new. For each: title, severity, confidence, status, file:line evidence, impact in

     CRITICAL: cross-tenant/cross-user data exposure, unauthenticated access to

     HIGH:     authorization gaps within a tenant, non-durable handling of important
               async work, money or compliance errors, serious reliability gaps
     MEDIUM:   contract drift, partial features, performance traps, missing audit
     LOW:      hygiene, documentation drift, minor inconsistencies
   Sort by severity, then confidence. If PREVIOUS_RUN exists, add a section:
   FIXED / STILL OPEN / NEW / REGRESSED.

   Each architectural or product decision evidenced in code or docs: decision,

   Highest-risk behaviors to test first, framework-agnostic, derived from the
   findings and diagrams: for each, the entry point or module, the scenario, the

   coverage across all entry points, idempotency and retry behavior of async work,
   failure of each external dependency, permission boundaries per role, and
   data-integrity invariants. Note which of these already have tests.

F. Optional, only if a test command is discoverable and safe to run offline:
